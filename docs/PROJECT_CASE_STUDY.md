# 项目案例：让个人记忆参与下一次判断

知衡是一个面向个人投资思考的本机 Personal Agent 验证项目。项目由个人提出需求、围绕实际使用反馈持续迭代，借助 AI 编程工具实现与测试。公开仓库展示产品取舍、架构和验证过程；目前没有商业用户数据、收益验证或线上规模指标。

## 从具体困境出发

用户原本基于行业需求观察一家公司，后来看到其他方向上涨，开始考虑调整。困难不只是缺少一份行情解释，而是原来的依据、眼前的触发和新的判断标准容易混淆。普通长对话也容易把“另一笔短线试仓”与原先讨论的交易关联到一起。

产品目标是帮助用户找回真实依据、核对变化、纠正理解并继续跟进。前台保持输入、回答、必要时展开来源的简单流程；不要求用户先填写交易体系，也不把投资结果当作产品正确性的证明。

## 本次迭代的关键决策

| 用户问题 | 产品与工程处理 | 保留的边界 |
| --- | --- | --- |
| 不同想法被混成一段历史 | 独立原文 + 显式回复链；按任务检索其他片段 | 不凭同股、同主题自动合并 |
| 用户得主动提醒模型找历史 | 理解当前任务，缺少原始依据时主动检索 | 材料已足够时不强行引用历史 |
| 标签只用于展示，没有改变结果 | 标签作为第三个候选通道，加入全文/向量 RRF | 标签相同不直接建立关系 |
| 找到旧卡片就当作当前事实 | 校验双方原话、来源、时间和任务关系后才引用 | 分数是启发式，不是置信概率 |
| 纠正之后下一次还会误用 | 持久反馈影响过滤、排序及上下文；旧状态失效 | 反馈限定情境，允许撤销与主动回看 |
| 多角色让输出更复杂 | 后台独立分析与质疑，统一结果，按需展开依据 | 同一模型的多角色不是多个独立信息源 |

## 一段可复现的验收流程

以下为虚构示例，不是投资建议或真实个人记录：

1. 保存“我关注青杉设备，是想验证订单是否兑现”。原文独立保存，标签引用原文依据。
2. 后续输入“青杉设备今天回落，其他方向上涨，我在考虑调整”。无需手动选历史卡片；当任务需要原始依据时，检索并验证关联。
3. 回答下展开关联原因和来源。如果实际是另一笔交易，直接说“这个关联不对，这是另一笔短线试仓”，或点“不是这件事”。
4. 在同一回复链继续讨论，检查错误来源不再作为当前依据；刷新后反馈仍存在。可撤销反馈，或明确要求重新查看历史原话。

入口：本机首页 → 输入；“我的脉络” → 原文和标签；回答下 → 关联来源及反馈。运行方式见 [README](../README.md#打开与开始使用)。

## 为什么没有继续堆组件

个人规模下，SQLite 同时保存原文、版本、任务和向量，避免引入独立向量数据库与分布式队列。后台 worker 承接已启动任务，模型负责理解与提出行动，程序校验并执行。应用保持自有检索与状态流程；当前没有引入 LangChain 或 LlamaIndex，架构取舍不等于否定这些框架。

“越用越聪明”目前特指：有来源的个人上下文逐渐积累，明确纠正实际改变下一次检索和引用；不指模型参数训练或随记录数量自动提高准确率。

下一步先建立涵盖“同股不同交易、观点过时、纠正后再询问”的标注评估集，比较各检索通道和反馈策略，再优化复杂任务延迟。每周回顾已在 v0.3.0 实现为单独的派生视图；大规模效果评估、全天在线和推送仍未实现。

## v0.3.0：从保存理解到定期帮助用户梳理

每周回顾提供一个开关和一个手动入口。程序用持久时段、唯一约束与事务调度；模型只负责在有界材料中归纳，不能用“我会提醒”替代执行。离线只补最近一期、失败不自动重试，避免恢复服务后突然产生多次费用。报告逐项引用原文，纠正后生成新版本，既不合并原始卡片，也不自动提炼为用户规则。

实现入口：[调度与生成](../server/weekly-review.ts)、[后台 worker](../server/worker.ts)、[交互](../app/weekly-review.tsx)、[边界测试](../tests/weekly-review.test.ts)、[真实模型验收脚本](../scripts/live-weekly-review.ts)。新增测试包含真实 worker 在没有浏览器时执行空周任务。个人规模优先复用现有 worker 与 SQLite，没有新增常驻调度服务。

## v0.4.0：从摘要转向可追溯的交易思路

用户反馈是“回顾没有把交易思路整理出来”。改动首先落在日常状态：保留原始依据、观察周期、触发、拟调整、明确验证/失效条件与用户报告的行动，用有原话证据的版本区分新信息、改计划、纠正和单纯结果。前端给出一条紧凑的判断脉络，无需新表单。

周回顾采用分阶段处理：真实回复链划定讨论边界 → 平衡抽样保留开始/最新表达 → 从状态定位原文并补相关历史 → 保留长文头尾 → 模型按情境梳理 → 程序校验引用与边界 → 独立模型核对语义。误把计划当成交等归纳不保存为成功。程序分组、采样、引用映射和时间校验是确定性算法，具体交易关系与逻辑判断仍依赖模型；相同模型的两次调用不构成两份独立事实证据。

这是减少“摘要看着完整、却没有还原决策”的一次迭代。尚未证明长期准确率提升；跨独立片段关联偏保守、讨论内多交易识别和长材料中段遗漏仍是局限。对应实现：[决策状态](../server/working-state.ts)、[情境与上下文选择](../server/decision-context.ts)、[回顾核对](../server/weekly-review.ts)、[场景测试](../tests/decision-logic.test.ts)。

## v0.4.1：修正过度隔离与上下文配额

实际反馈揭示“有 RAG”和“有引用”仍不足以整理思路：逐条均分预算会截掉长论证核心，缺少历史回复链又让同一问题被拆成多条摘要。改为共享原文预算，短记录让出空间；用原文片段编号提出接续、背景、对照三类关系，由程序构建本期分组并限制写作引用。背景与对照不合并交易，拒绝关系具有优先级，原始记录始终独立。

确定性部分负责预算分配、分组归并、引用还原、否认关系检查与版本失效；模型负责有依据的关系判断、逻辑链整理和独立核对。分组短编号、允许引用清单和元数据诊断降低格式错误成本，仍不能证明语义正确。生成报告不是闭环终点：候选验证可以带回对应讨论继续处理，用户无需重述背景，也不会因点击入口就被视为认可规则。新增测试使用合成材料；真实失败与复测结论如实记载于 TESTING.md，不公开私人内容或声称准确率。

后续实测说明，仅提供分组规则仍不足以避免跨组引用，因此改为最多3个重点问题分别生成：程序在调用前隔离材料，独立对照阶段才提供两端原文，最后统一核对。回复链也只作线索，不自动归并交易。新增测试检验输入隔离本身，而非仅模拟正确答案；模型仍可误判关系和含义，保留纠正、删除与失败状态。

核对结果也决定交付范围：独立写作没有读取后续比较，因此可在比较被否定时保留已审阅的独立逻辑，删除比较及其关系并显式标为部分完成。核心逻辑或背景关联有错误仍阻止交付。该降级路径避免一条缺乏依据的共同模式丢掉全部整理，也不把部分通过包装为整份可靠。
