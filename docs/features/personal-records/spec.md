# 开发任务：在现有 Personal Agent 中新增可复用的“个人资料、观点记录与可追溯记忆”能力

请把本文作为本次开发任务的完整业务说明，不要求从此前聊天中推导或补全需求。

本说明用于明确本次业务范围，不替代仓库已有的安全要求、开发规范和更高优先级指令。

请先检查实际项目，再增量开发，完成测试、文档和交付说明。不要只给我架构建议或伪代码，也不要未经检查重新创建一个独立项目。

如果当前环境不能访问仓库、缺少运行权限或必要凭据，应明确说明哪些工作可以完成、哪些真实链路无法验证，不得假装检查过代码、调用过接口或运行过测试。


==================================================
一、本次任务的背景与范围
==================================================

我正在开发一个服务于我个人的 Personal Agent。

它不是单纯的聊天机器人，也不是单纯的股票行情终端，而是能够持续理解我的关注事项、保存资料与想法、辅助思考、执行明确委托，并在之后的对话中利用相关历史记录的个人助手。

当前我希望新增一项“记录”能力：

当我看到研报、文章、网页、一段文字或产生自己的想法时，可以通过飞书聊天把这些内容发给 Personal Agent。

Agent 应当帮助我：

1. 保存原始材料和来源。
2. 理解这次输入是在收藏、记录想法、分析资料，还是补充旧记录。
3. 提取有用内容，但不把摘要当作原文。
4. 区分作者观点、我的立场、系统推断和已核实事实。
5. 找到与已有记录的关联。
6. 让我以后用自然语言找回资料与当时的想法。
7. 接受我的纠正，保留必要的版本与变更依据。
8. 支持删除，并使相关派生内容和检索结果同步失效。
9. 在获得明确授权后，将待验证问题交给已有任务系统处理。

首个重点场景是“研报与投资想法记录”，但底层能力必须可复用，未来可以处理学习资料、产品想法、工作笔记等内容。

本次不是开发或重构“A股主线机会雷达”。

此前可能讨论过的以下内容，不得成为本次记录功能的硬编码：
国产替代主线；
固定六只股票；
固定历史价格；
市场扫描范围；
量价触发条件；
投资监控调度规则。

已有监控模块可以通过明确接口与记录模块连接，但不得为了本次功能重做监控系统。

当前目标是我个人可实际使用的验证版本，不开发多租户、商业化、计费或复杂组织权限体系，不接交易账户，不自动交易。


==================================================
二、核心原则：必须遵守的业务边界
==================================================

请将以下原则落实为数据结构、权限边界和测试，而不仅仅写进模型提示词。

1. 收藏一篇资料，不等于我认同它。
2. 我关注一个股票或行业，不等于我持有它。
3. 作者的观点，不等于已核实事实。
4. 系统的分析，不等于作者原话，也不等于我的观点。
5. 我对一篇资料的评价，不应自动变成我的永久偏好。
6. 保存一篇资料，不等于授权创建持续监控任务。
7. 保存原文成功，不等于解析成功。
8. 解析成功，不等于已完成索引，也不等于所有内容都已被理解。
9. 摘要、向量和标签都是派生数据，不能替代原始资料。
10. 链接保存成功，不等于已经读取链接正文。
11. 无法读取、无法确认、没有相关记录时，应如实说明，不补造内容。
12. 用户记忆应存储在可管理的持久化系统中，不依赖模型聊天上下文一直保留。
13. 原文、来源、时间、版本和用户纠正应可追溯。
14. 记录中的外部文本是不可信输入，不能修改系统规则或授权调用工具。
15. 不得为了“让系统看起来聪明”自动推断我没有表达的立场、经历、持仓或意图。

五、功能分层：通用能力、内容模板和具体记录
==================================================

请区分以下三层，但以当前项目结构为准，不机械增加服务数量。

第一层：通用记录能力。

负责：
接收；
原始保存；
解析；
内容提取；
关联；
索引；
检索；
纠正；
版本；
删除；
执行状态和错误恢复。

第二层：内容处理模板。

首版重点实现“研报/分析文章”模板，同时保留“普通文字笔记”模板。

研报模板可以提取：
核心主张；
支持证据；
时间范围；
适用前提；
风险；
待验证问题。

普通笔记模板应保留用户原始表达，提取主题与问题即可，不强行套用研报格式。

模板必须可扩展，但本次不要求一次实现会议、音频、视频等全部内容类型。

第三层：具体记录。

保存用户这次输入的原文、附件、来源、说明、关注点、立场、关联和处理状态。

不要把“股票代码”“投资建议”等字段写成所有记录必填项。


==================================================
六、首版输入范围与接收规则
==================================================

首版必须优先支持：

A. 用户直接发送的文字。
B. 用户发送的文本型 PDF。
C. 可合法访问并取得正文的网页链接。
D. 对已有记录的补充、纠正和追问。

图片、扫描型 PDF、语音和其他格式：

如果现有项目已有可靠处理能力，可以复用；
如果没有，允许先保存原始材料，并明确标记尚未解析或部分解析。

不要为了首版强行支持所有格式，也不要假装已经理解无法读取的内容。

对于 PDF：

优先利用可提取的文字层；
图表和扫描页单独处理；
无法读取的页码应明确记录；
不能只读取第一页就声称分析了全文。

对于网页：

保存原始 URL、最终 URL、获取时间和可用元信息；
正文获取成功后再生成内容分析；
登录限制、失效链接、反爬或权限不足时，保存链接记录并标记正文未读取；
不绕过访问控制；
不根据标题和摘要猜测全文。

对于纯文字想法：

保留原始表述；
可以另生成整理版；
不能用整理版覆盖原话；
不能改变语气强度，例如把“我有点怀疑”改成“用户明确反对”。

多个附件同时发送时，应有清楚的批次和材料关联，不能把多个独立文件误当一份报告。


==================================================
七、意图识别与默认行为
==================================================

需要识别至少以下意图：

收藏资料；
记录个人想法；
分析但不长期收藏；
补充已有记录；
纠正已有记录；
检索记录；
对比资料；
删除记录；
明确委托后续任务。

示例：

“这篇存一下”
→ 收藏资料。

“这篇存一下，我不认同它对需求的判断”
→ 收藏资料，并记录用户针对特定判断的立场。

“帮我分析这篇有什么问题”
→ 分析请求。除非用户已有明确默认设置，否则不自动加入长期资料库。
正常会话日志与主动收藏应区分。

“记一下，我现在觉得这条逻辑还需要验证”
→ 保存用户想法，不需要凭空创建一份外部资料。

“这篇和我上次存的那篇对比一下”
→ 检索并对比，不擅自改变两篇记录的结论。

“以后出现能验证它的新证据时提醒我”
→ 明确的后续任务意图，转入已有任务系统的授权和配置流程。

对直接发送文件但没有文字说明的情况：

支持配置“资料收集模式”。
在用户明确开启的收集入口中，可以默认收录。
普通聊天中没有明确默认策略时，应进行轻量澄清或生成待确认条目，不能对所有输入一律永久收藏。

不要每篇都强迫用户填写标签、摘要和收藏原因。

收藏原因未知时，可以保存：
关注原因：未说明。
用户立场：未知。

不得为了字段完整而猜测。


==================================================
八、必须实现的核心交互场景
==================================================

场景1：发送研报并说明疑问

用户发送 PDF，并说：

“帮我收一下。我主要想知道里面说的需求改善是不是真的。”

系统应：

保存原文；
解析内容；
提取作者的需求改善主张及其证据；
保存用户关注的问题；
将用户立场标记为待验证，而不是看多；
检索相关旧记录；
返回简短记录卡。

记录卡示意：

已收录：某行业研究报告

作者主要观点：
……

你关注的问题：
需求改善是否已经发生，还是对未来的预测。

相关旧记录：
……，或“暂未找到可靠关联”。

尚待验证：
……

状态：
原文已保存；正文已解析；检索已就绪。
用户立场：待验证。

示意内容不能作为真实研报数据写入生产环境。


场景2：没有附加说明的收藏

用户说：
“这篇保存一下。”

系统完成保存和整理，但不推断收藏动机或认同程度，不反复询问非必要问题。


场景3：记录个人想法

用户说：
“我觉得这个行业现在的问题不是需求，而是利润兑现，先记一下。”

系统保留原话，并形成一条个人观点记录。
可以关联已有主题，但不能将这句话变成已验证市场事实。


场景4：用户纠正系统理解

用户回复：
“我不是看好这个行业，我只是想学习这篇文章分析库存的方法。”

系统应：
将本条记录的收藏目的调整为方法学习；
撤销不恰当的行业看多推断；
更新关联和检索信息；
保留必要变更记录；
不推导出“用户永远不关注这个行业”。

若同一对话有多条可能被指代的记录，应确认目标，不能修改错记录。


场景5：自然语言找回

用户说：
“我上次存的那篇，我觉得需求改善证据不够的报告，帮我找出来。”

系统应结合：
内容主题；
用户疑问；
收藏时间；
原文和个人批注；
找到候选记录并提供依据。

存在多个相近结果时，展示少量候选及匹配原因，不伪装成唯一确定结果。


场景6：重复发送

完全相同文件再次发送：
复用已保存原始资产，避免重复解析和重复索引。

但本次附加的想法不同：
必须保存新的用户批注和提交关系，不能简单丢弃整条消息。

同标题但不同日期或不同内容：
应识别为可能的新版本或不同资料，不能按标题直接去重。


场景7：读取失败

链接无法访问或 PDF 部分页面无法读取：
明确显示已保存什么、没有读取什么。
不生成假装覆盖全文的摘要。
允许之后重试或补充文件。


场景8：新资料与旧观点相关

新资料涉及旧记录中的待验证问题：
生成有来源的关联建议。

如果涉及不同统计时间、口径或对象，应先标记差异，不能直接说“旧观点被证伪”。


场景9：删除

用户要求删除指定记录：
明确删除范围；
对有歧义或不可逆操作执行必要确认；
完成数据库、派生内容和索引清理；
在后续检索和回答中不再引用已删除内容。

不得显示删除成功，但相关观点仍通过旧索引持续进入回答。


==================================================
九、如何实现“智能整理”
==================================================

智能整理不等于生成一篇很长的摘要。

请优先提取以后可以检索、对比和验证的内容。

对于研报或分析文章，按实际内容提取：

1. 基本信息：
标题、作者或机构、发布日期、资料类型、收录时间。
无法确认的字段为空或标记未知。

2. 核心主张：
作者在判断什么；
针对什么对象；
涉及什么时间范围；
属于历史描述、当前判断还是未来预测。

3. 支持依据：
作者引用的数据、事件和论据；
对应原文位置；
数据单位、区间和来源。

4. 成立前提：
原文明示的条件；
与系统提出的分析前提分开保存。

5. 风险或反向信息：
原文列出的风险；
系统提出的待核查疑点。
两者分别标注来源。

6. 待验证问题：
哪些结论仍缺证据；
未来需要什么类型的信息才能进一步判断。
这里只形成问题，不自动启动监控。

7. 用户关注点：
仅来自用户表达或明确确认的历史上下文。
不得根据报告内容直接代替用户设定立场。

8. 简短展示摘要：
用于快速查看，不替代上述结构化内容。

不要求每篇填满所有字段。
没有某类信息时保留缺失，不能为完整性而编造。

对于长文：

按结构解析和分段提取，再汇总；
保留跨段落的来源对应关系；
不能把全部历史记录无差别塞进一个模型请求；
不能遗漏大量正文后仍声称全文处理完成。

对于表格和数字：

保留表头、对象、时间、单位及上下文；
不能把不同单位或不同期间的数据拼接成新结论；
证据定位不可靠时，标记需要复核。

结构化模型输出应进行格式验证与业务校验。
修复失败时进入可见的失败或部分完成状态，不静默写入异常结构。


==================================================
十、证据和来源必须可追溯
==================================================

每条重要提取结果应关联原始资料中的具体位置。

可以根据内容类型使用：

PDF物理页码与文本片段；
网页标题层级、段落和文本定位；
文字消息ID与引用范围；
记录版本和对应内容片段。

页码需要说明口径，避免把PDF物理页码与正文印刷页码混淆。

不得生成不存在的页码、段落或引用。

至少区分：

原文直接支持；
用户明确表达；
系统推断；
外部验证结果；
尚未验证。

作者引用的数据默认只是“资料中记载的数据”，除非确实执行过外部核验，否则不能标为系统已验证。

模型使用的版本、提取模板版本和处理时间应可追踪。
不要求保存隐藏推理过程；保存可核查的证据、计算或简要判断理由即可。

同一原始来源被多个网站转载，不应被视为多份独立证据。
能够确认转载关系时保存来源链；不能确认时不要强行合并。


==================================================
十一、个人观点、记忆和资料必须分开
==================================================

至少区分以下逻辑对象：

原始资料；
资料中的主张；
用户对资料或具体主张的批注；
用户的问题；
系统的关联和推断；
经过授权的长期用户记忆；
后续任务。

用户可以认可一篇文章中的一个观点，同时质疑另一个观点。
不要只给整篇资料设置一个粗糙的“同意/不同意”并覆盖所有细节。

用户立场可以包含：
未表达；
关注；
待验证；
部分认同；
认同；
质疑；
反对。

这些状态应有证据或用户确认，不由系统随意填充。

从单篇资料推断出的偏好，最多形成候选建议。
未经充分依据或明确授权，不升级为长期用户事实。

用户改变想法时：
保留旧立场的时间与新立场的时间；
记录变化依据；
默认回答当前立场；
在复盘时允许查看历史变化。

不把最新立场倒填到过去，不让系统声称用户一直如此认为。

当前任务不涉及训练或微调模型。
“放进大脑”指外部可管理的持久化资料与记忆，以及按需检索和使用。


==================================================
十二、关联旧记录与发现新增信息
==================================================

请实现有证据的关联，而不是随机推荐相似文章。

可以使用：
相同对象；
相同问题；
同类方法；
共同数据来源；
相近时间范围；
相同或相反的主张；
用户已明确建立的主题关系。

关联类型可以包括：
相关；
补充；
重复；
可能支持；
可能存在冲突；
新版本；
方法参考；
需要进一步对比。

自动关联应标记为系统建议，允许用户接受、纠正或移除。

判断冲突前至少比较：
对象是否相同；
讨论期间是否相同；
统计口径是否一致；
是事实描述还是预测；
前提条件是否不同。

两份资料结论不同，不一定构成逻辑冲突。

应尽量回答：
这篇资料对已有记录新增了什么；
哪些内容只是重复；
哪些旧问题得到更多材料；
哪些问题仍然无法确认。

没有找到可靠关联时，直接显示没有找到，不勉强建立关系。

首版可以用关系表实现，不要求知识图谱数据库。
不能仅靠把资料归到同一个标签，就宣称完成了知识关联。


==================================================
十三、检索与之后的使用方式
==================================================

检索应覆盖：

资料标题和正文；
用户的收藏原因、批注和疑问；
标签与实体；
时间、来源和资料类型；
有效版本和关联关系。

优先复用现有检索能力。

可以结合：
结构化过滤；
关键词或全文检索；
语义检索；
必要的重排序。

不要把向量检索作为唯一手段。
股票代码、数字、日期、机构名称和精确短语需要可靠匹配。

如果尚未配置可用的向量模型：
应保留基础检索能力；
明确语义检索尚未启用；
不使用随机向量或演示数据冒充真实语义检索。

回答流程应是：

理解当前问题；
定位相关记录；
读取必要原文和用户批注；
生成有来源的回答；
说明缺失信息和不确定性。

不把所有历史资料一次性注入模型。

检索必须过滤：
无权限内容；
已删除内容；
被撤销的系统推断；
不应作为当前状态使用的旧版本。

历史版本可用于用户明确要求的复盘，但应标明时间和版本。

如果旧聊天摘要与当前纠正后的记录冲突，应以有效记录和明确的更新为依据，不继续传播旧误解。

资料尚未完成解析但已保存时：
用户按文件名查找应能找到；
回答应说明正文尚不可完整检索；
不能因此谎称资料不存在。

用户追问“这个观点现在是否得到验证”时：
先找回当时的主张和验证条件；
只有取得可靠的新证据后才能讨论验证结果；
没有新数据时明确说尚无法核实；
不能只凭保存过的旧资料冒充最新判断。


==================================================
十四、处理流程、状态与故障恢复
==================================================

请把接收、持久化和内容处理解耦，不让一个长文件解析阻塞整个聊天入口。

建议流程：

收到消息；
验证身份与消息合法性；
保存消息和接收事件；
保存原始材料；
建立记录与处理作业；
解析；
提取；
关联；
索引；
生成或更新记录卡；
保存发送结果。

事件回执与面向用户的“保存成功”是不同概念。
原始材料尚未持久化成功时，不得回复已经保存。

状态可以按项目风格实现，但要区分：

原始内容保存状态；
解析状态；
提取状态；
关联状态；
索引状态；
通知状态。

不要只使用一个success字段覆盖全部阶段。

例如：
原文已保存、解析失败；
正文已解析、语义索引待配置；
大部分页面已读取、部分页待处理；
记录完成、通知发送失败。

这些都应能准确表达。

后台处理需要：

持久化作业；
幂等操作；
有限重试与退避；
超时处理；
进程重启后的恢复；
明确的失败原因；
避免同一记录被并发重复处理。

优先复用已有任务框架，规模不需要时不要引入复杂分布式组件。

必须区分：

消息事件去重；
原始资产去重；
本次收录行为；
用户新增批注；
处理作业去重；
通知去重。

同文件重复发送，不等于重复发送时附带的用户想法可以丢弃。

同链接不同时间获取到的新正文，不应仅凭URL相同被永久忽略。

处理过程中用户修改或删除记录时，要处理版本冲突，避免旧作业完成后把已经撤销的内容重新写回来。


==================================================
十五、数据模型与接口要求
==================================================

请先复用现有模型，再决定如何扩展。

以下是逻辑对象要求，不强制每项都独立建表：

1. 原始资产：
文件或正文、内容哈希、类型、大小、存储位置、来源。

2. 接收与收录事件：
用户、渠道、消息、会话、接收时间、本次说明、幂等标识。

3. 记录：
标题、类型、关注目的、所有者、状态、当前版本。

4. 解析片段：
正文、章节、页码或段落、来源定位、解析版本。

5. 主张与证据：
主张内容、对象、时间范围、类型、来源、验证状态。

6. 用户批注：
原话、整理版、立场、关联对象、时间、修订关系。

7. 关联：
来源记录、目标记录、关系类型、依据、生成者、确认状态。

8. 处理作业：
阶段、版本、重试次数、错误、时间、结果。

9. 检索索引：
所属记录、片段、版本、索引状态。

10. 通知与操作审计：
通知目标、发送状态、关键操作及结果。

用户身份和记录所有权必须由服务端鉴权确定，不能允许模型随意填写另一个用户ID访问记录。

内部工具可以包括以下语义能力，具体命名遵循项目约定：

创建记录；
查看记录与处理状态；
添加批注；
搜索记录；
读取证据；
对比记录；
纠正记录；
查看版本；
删除记录；
重试处理；
创建后续任务草稿。

工具返回应包含：
成功或失败；
操作ID；
记录ID；
当前状态；
实际完成的阶段；
证据或错误；
是否需要用户确认。

主 Agent 应通过受控工具访问数据，不直接拼接任意数据库操作。

大模型可以提出结构化提取和关联建议，最终写入应经过程序验证和权限检查。


==================================================
十六、飞书交互与入口整合
==================================================

复用项目已有飞书接入。
如果缺失，按当前官方文档核实并实现适用于用户消息接收的应用能力。

不要把只有向外发送消息的Webhook当作已经完成双向聊天接入。

涉及事件类型、权限、文件下载、消息回复和卡片操作时，应核实当前官方文档，不凭记忆编造API字段或权限名称。

需要处理：
消息ID；
用户ID；
会话ID；
回复目标；
附件关系；
事件重复投递；
用户针对某张记录卡的后续操作。

只处理授权用户或授权会话。

首版不要求复杂后台界面，优先完成飞书聊天中的闭环，并复用现有管理页面展示记录和状态。

记录卡应简短，默认展示：
标题；
保存和处理状态；
少量核心内容；
用户关注点；
最重要的关联或待验证问题；
查看原文、补充想法、纠正等入口。

长篇分析按用户追问展开，不要每次上传都向聊天发送数千字。

对长任务：
可先发出真实的阶段性状态；
完成后更新原卡，或发送一次最终结果；
避免每个内部阶段各发一条消息。

用户回复“不是这个意思”时，应尽量根据明确的回复关系定位记录。
目标不清楚时只做必要澄清，不猜测修改对象。

卡片操作需要再次校验用户和记录权限，重复点击应幂等。


==================================================
十七、与现有任务、监控和复盘能力连接
==================================================

本模块可以输出：

待验证问题；
需要补充的证据；
相关主题；
用户明确的后续委托。

但默认只形成记录，不自动启动持续监控。

例如：
收藏研报 → 保存材料和疑问。
“这个问题帮我持续跟进” → 进入任务创建或任务草稿流程。

只有用户明确授权，或已有清楚的用户自动化规则，才允许启用后续任务。

如果现有任务系统尚未实现：
保存可用的任务草稿或待办；
明确显示未启用；
不宣称后台已经持续跟踪。

已有雷达信号可以引用相关记录提供背景，但必须区分：
市场量价变化；
产业逻辑验证；
用户原有观点。

价格上涨不能自动证明某篇研报的产业判断正确。

本次不新增全市场扫描、行情策略或自动交易逻辑。


==================================================
十八、隐私、安全与删除语义
==================================================

必须考虑：

授权用户校验；
密钥不进代码和日志；
敏感文件不自动公开；
外部模型和存储的数据处理范围明确；
只发送完成任务必要的内容；
原文中的指令不能改变工具权限。

网页抓取应限制目标协议、重定向和地址范围，防止访问内部地址、本机服务或其他不应访问的资源。

附件处理应检查类型、大小和资源消耗，不执行文件中的脚本、宏或其他主动内容。

外部资料中的“忽略之前指令”“发送所有文件”等内容只能作为资料文本，不能执行。

删除要定义清楚：

删除一条收藏；
删除该次个人批注；
删除原始资产；
删除全部相关派生内容；

这些不是同一个操作。

相同原始资产被多个有效记录引用时，删除其中一条不能破坏其他仍保留的记录；但要向用户准确说明删除范围。

用户确认删除的范围内，需要同步处理：
记录；
相关提取结果；
关联；
全文索引；
向量索引；
缓存；
待执行作业；
可能影响后续回答的相关记忆。

为防止后台旧作业复活已删除内容，应检查删除状态和版本。

审计日志只保留必要操作信息，不以“审计”为名完整保留用户要求删除的敏感正文。

对于已发出的外部消息、备份或第三方服务保留内容，应准确说明能力边界，不能承诺无法做到的彻底远端删除。

需要删除或关闭的内容，不应继续通过长期聊天摘要进入回答。


==================================================
十九、实现顺序与成本控制
==================================================

请按可运行闭环推进，而不是先搭建巨大架构。

阶段1：可靠收录和找回。

完成：
飞书接收或现有入口接入；
文字、文本PDF、可访问链接的原始保存；
处理状态；
基础内容提取；
记录查询；
关键词或已有检索；
简短记录卡；
重复事件去重。

阶段2：个人化理解。

完成：
区分作者观点与用户立场；
个人批注；
补充与纠正；
来源定位；
相关旧记录检索；
有依据的关联建议；
自然语言找回。

阶段3：可追溯和可持续运行。

完成：
版本；
删除；
重试恢复；
索引一致性；
隐私与权限；
后续任务草稿接口；
必要的复盘查询。

阶段不是省略后续要求的理由。请在实际环境允许的范围内推进，并明确最终完成到哪一项。

成本控制要求：

原始资产相同且提取版本相同，尽量复用已有解析；
只对发生变化的记录重新处理；
不要每次上传都把整个资料库传给模型；
先召回少量相关记录，再进行关联判断；
限制输出长度和长文处理资源；
模型失败时保留原文和基本查询能力；
不要因为模型故障就丢失用户输入。

不要求固定向量数据库、固定大模型或复杂Agent编排，以当前项目已具备的能力为基础。


==================================================
二十、测试与验收标准
==================================================

请建立自动化测试和必要的真实链路验收。

测试数据必须与生产记录隔离，不向真实通知渠道发送测试消息，除非得到明确授权。

至少覆盖以下场景：

A. 原文与状态
- 文件保存失败时不能显示已保存。
- 解析失败但原文已保存时状态正确。
- PDF只读到部分页面时不能声称全文分析。
- 链接无法访问时不编造摘要。

B. 意图与立场
- 收藏看多报告，不得生成“用户看多”。
- 用户说不认同某判断，能正确记录局部立场。
- 只请求分析时，不擅自加入长期收藏。
- 单篇方法参考，不升级为用户行业偏好。

C. 重复与版本
- 同一消息重复投递只产生一次收录结果。
- 同一文件再次发送但批注不同，文件复用、批注保留。
- 同名不同内容不误合并。
- 修改记录时旧后台作业不能覆盖新版本。

D. 检索与证据
- 按用户疑问而非文件名能找到正确记录。
- 精确代码、日期、数字能合理匹配。
- 引用页码或段落真实存在。
- 多个候选时不强行唯一匹配。
- 当前检索不继续引用已撤销推断和旧立场。
- 记录已保存但未索引时能显示真实状态。

E. 关联
- 重复转载不当作独立证据。
- 不同期间的数据不直接判定互相矛盾。
- 系统关联建议与用户确认区分。
- 用户移除错误关联后不会立即被同一逻辑反复恢复。

F. 删除与安全
- 已删除内容不再进入检索和回答。
- 删除后未完成作业不能重建记录。
- 无权限用户不能读取记录或操作卡片。
- 外部文档中的恶意指令不能触发工具调用或数据泄露。
- 网页抓取和文件解析的限制有效。

G. 运行可靠性
- 模型不可用时仍能保存原始输入。
- 重启后可恢复未完成作业。
- 推送失败不导致记录丢失。
- 并发上传不会串联到错误记录。
- 多条记录的模糊追问不会误改对象。

请区分：
使用测试替身通过的单元测试；
真实模型测试；
真实飞书接入测试；
端到端验证。

不能把前者包装成后者。

可以使用虚构研报和笔记作为测试样本，但必须明确标记测试数据，不能混入用户真实资料。
